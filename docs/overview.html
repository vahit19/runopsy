Runopsy

Causal failure analysis for AI agent runs — an end-to-end overview.

What it is. A local-first command-line tool that records what an AI agent did, then works out where the run started going wrong — not where it stopped — and shows the evidence for that claim. It can then re-run the trace with one thing changed to test whether the claim holds.

The problem it exists for

When an agent run fails, the last error is rarely the problem. An agent writes a config for the wrong environment at step 9; nothing complains. Five steps later a test fails because it cannot reach the endpoint. You read the log bottom-up, see the failing test, and spend an hour on the test.

The failure was at step 9. The symptom was at step 14. Everything between them was successful, so nothing in the log points backwards.

Measured: blaming the last failing step — which is what reading a log bottom-up achieves — identifies the true onset 22.2% of the time on a labelled suite. Runopsy's deterministic engine: 94.4%.

The distinguishing move is not the visualisation, which anyone could rebuild. It is that Runopsy will try to prove itself wrong: runopsy replay --execute re-runs the trace in a disposable sandbox with one intervention at the suspected onset, and only upgrades a suspicion to a cause when the downstream failures actually disappear.

Three rules the design cannot break

  • Local-first. Traces, state and artifacts stay on your machine. Nothing reaches a provider without explicit opt-in.
  • Deterministic-first. The core analysis spends zero tokens and makes zero network calls. A model is optional and budget-capped.
  • Calibrated language. A finding stays suspected onset until a replay or a named human says otherwise. "Definitive root cause" is not available.

How it works: the chain, end to end

1 · CaptureA runtime adapter hooks the agent. One runopsy hook process per event.
→
2 · NormalizeRuntime events become a typed graph: nodes and edges, OpenInference-compatible.
→
3 · Detect15 detectors read the graph and emit signals: failures, loops, state conflicts.
→
4 · RankSignals become ordered candidates, scored by severity, precedence, impact.
→
5 · ValidateA sandboxed replay with one intervention tests the top candidate.

Storage: two halves, on purpose

JSONL journal — append-only, one file per run, authoritative. Written first and sealed with a rolling digest as it goes.  ·  DuckDB index — derived, queryable, rebuildable from the journal. Reading reconciles the two.

Why: DuckDB admits one writing process. An agent with parallel subagents fires several hooks at once, so index writes are lost as a matter of course. The journal must survive that alone — and does.

The five analysis layers

L0 structural Facts the runtime already reported: exit codes, statuses, timeouts, missing events. Nothing is interpreted, so nothing can be wrong about meaning. zero tokens
L1 behavioral Patterns across steps: unproductive loops, retry storms, state that keeps flipping back. zero tokens
L2 graph impact What the onset could have reached — reachability forward in time only, drawn as inference, never as record. zero tokens
L3 semantic A model reads the few steps already found suspicious. Opt-in, budget-capped, cannot raise a status. costs money
L4 validation Counterfactual replay, or a named human. The only thing that can call something a cause. sandboxed

The three statuses, which are never collapsed

StatusMeansConfidence
observed failureWhat the run visibly got wrong. A fact.—
suspected onsetWhere it may have started. Correlation and ordering.capped below 0.75
replay-supportedChanging it made the downstream failures disappear.up to 0.9
Temporal order plus correlation is not causal proof, and the output never says it is. A guard in the code (asserts_causation) fails the build if any output path claims causation for an unvalidated finding.

The commands that matter

CommandWhat it does
demoA worked example, no setup, no key. Start here.
record / runWrap a pipeline, or drive an agent and diagnose it in one step.
diagnoseObserved failure, suspected onset, what it may have reached. --mode hybrid adds the paid layer.
evidence --step NThe command, its output, the repository changes, and why the step ranked where it did.
replay --from-step NPlans a controlled re-run; --execute tests it in a sandbox.
verifyWhether a trace is byte-for-byte the one recorded. Tamper evidence, not tamper proofing.
graph / export / uiASCII timeline · self-contained HTML report or OTLP · browser view, loopback only.
benchScore the engine: synthetic suite, fault injection, or an external labelled corpus.
doctor / setup / configStore health and credentials · key into the OS keyring · runopsy.toml.

What it will not do

  • Claim a cause it has not validated.
  • Send anything anywhere without --mode hybrid.
  • Execute a replay outside a disposable sandbox, or perform a blocked side effect — an unrecognised tool needs human approval, failing closed.
  • Report a finding on a healthy run. The false-positive rate is exactly zero.

The eleven packages

runopsy is the meta-distribution pip install runopsy resolves to. Below it, so a library user can depend on one piece: core (schema, detectors, ranking — needs only Pydantic) · collector (journals, index, vault, retention) · cli · replay (checkpoint restore, counterfactual execution) · bench (cases, metrics, fault injection, external benchmarks) · adapter (shell + Hermes) · semantic (the paid layer) · server (API + web view) · ui (React) · inspect (Inspect AI logs).

runopsy-core never imports runtime-specific code — it accepts only the normalized graph. That is what makes a second runtime adapter possible.

The four measurements — including the ones that go badly

BenchmarkWhat it measuresOnset top-1
Runopsy-Bench (20 synthetic)Does the ranking behave as designed94.4%
— baseline: blame the last failureWhat reading a log achieves22.2%
Fault injection into a real recorded runCan it find a known break in a real trace100%
TRAIL — expert-labelled SWE-Bench tracesDoes it agree with human experts on real coding agents0.0%
Who&When — expert-labelled multi-agentThe same, on conversation traces0.0%
Why the last two are published. Runopsy localizes onsets that were themselves failures — a step that errored before the visible symptom did. On TRAIL, not one of the 30 annotated onsets carries an error status of any kind: they are formatting mistakes, instruction non-compliance, a wrong assumption about a file path. The deterministic layers read exit codes, so they are blind to those by construction. The 94.4% and the 0.0% describe the same engine on different kinds of failure, and a page carrying only the first would be selling rather than measuring.

Honest limits, as of version 0.1.7

  • Seven of fifteen detectors have fired on a real recorded run. Three cannot fire on one at all — they need fields or event kinds no current adapter produces.
  • One live runtime adapter. The architecture is runtime-agnostic; only Hermes proves it so far.
  • No corpus of our own. runopsy label exists; the corpus is empty. Filling it needs a person reading real failures — doing it from inside the project would grade the engine against its own opinion.
  • Semantic localization is unmeasured. The layer that could answer TRAIL has not been scored on it.

Where it goes next

1. Record more real runs — every headline number except the injection one still comes from traces the project wrote itself.  2. Score the semantic layer on TRAIL, the case the deterministic engine misses by design.  3. Give retry_storm something real to fire on, or remove it.  4. A second live runtime adapter.
