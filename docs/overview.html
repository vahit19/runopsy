Runopsy

A local, open-source tool that finds where a failed AI agent run started going wrong.

1 · What is going on out there?

Developers now hand some of their work to AI agents. An agent is a program that carries out a task one move at a time: it reads files, writes code, runs terminal commands, runs tests. We will call each of those moves a step, and the whole thing from beginning to end a run.

Sometimes the agent fails the task. What is left is a long log, and the question "where did this go wrong?" to answer on your own.

2 · Where a failure shows is not where it happened

You tell the agent "fix that failing test." It runs 16 steps:

StepWhat it didResult
1–8Read files, searched, plannedfine
9Wrote a config file for the wrong environmenterrored — and the agent carried on
10–13Edited code, restarted the service, checked itall succeeded
14Ran the testfailed

You read the log bottom-up — everybody does — and you see step 14, the failing test. You spend an hour on that test.

The fault was at step 9. The agent wrote the wrong setting there, the next four steps ran perfectly well, and the thing only blew up at step 14. Nothing in between says "look here", because nothing in between failed.

How often does that mislead you? Measured on 20 runs whose answer was known in advance. "Blame the last failing step" — reading the log bottom-up — finds the real beginning only 22.2% of the time. Four times in five you look in the wrong place.

3 · What Runopsy does

It quietly records every step while the agent works. When the run ends it reads that record and says where things started going wrong — not where they blew up. Then it shows the evidence, and if you want it tests its own claim: it re-runs the run in a throwaway copy and changes only that step. If the later failures really do disappear, a suspicion is promoted to evidence. If they do not, it says so.

The name is Run + Autopsy: an autopsy looks for the cause, not the moment of death.

5 · Where does Runopsy sit?

This is the point people most often get wrong, so plainly: Runopsy is not a coding assistant and contains no coding assistant. It writes no code, holds no conversation, calls no model. The agent that writes the code is a separate program and you install it yourself. Runopsy attaches beside it.

Youterminal
→
Coding agentHermes — installed separately, writes the code
→
Model providerthe agent's own key, the agent's own account
↓  a one-line notice on every step (a hook)
Runopsyrecords · diagnoses · shows evidence · runs the experiment
The arrows go one way: Runopsy is told, it does not intervene. It never stops the agent or changes its decisions.
What is a "hook"? Some programs can be configured to "run this command whenever you do that". Hermes has that feature. Setup tells Hermes to run runopsy hook after every tool call, so a small notice reaches Runopsy each time the agent takes a step. Nothing has to be added inside Hermes — which is why no fork of it was ever needed.

One environment, or two separate programs?

Two programs inside, but one command line for you. There are three ways to use it and the diagnosis comes from the same place in all three:

ShapeHowWho writes the code
A · Runopsy starts the agent
the practical one		 runopsy run "fix the test" — Runopsy invokes Hermes through its own documented command line, waits, then diagnoses Hermes
B · You start the agent Use Hermes exactly as you always do; Runopsy records behind it. Then runopsy diagnose latest Hermes
C · No agent at all runopsy record -s "make" -s "pytest" — wraps your own commands You

So "install Runopsy and get both coding and autopsy in one place" is true for shape A: you type one command, the agent does the coding, Runopsy does the diagnosis. The agent simply does not ship inside Runopsy.

The agent is still not a dependency. pip install 'runopsy[hermes]' installs both and runopsy init wires them together in one command — but plain pip install runopsy brings no agent at all and works fully on its own. That is not a detail, it is the principle: the analysis engine does not require any particular runtime to exist, and that is exactly what makes supporting a second agent possible.

6 · How many API keys do you need?

There are two separate keys and they have nothing to do with each other:

KeyWhoseWhen it is needed
The agent's key
runs the model that writes code		 Hermes'. It goes in Hermes' own config; Runopsy never sees it. Required if you work with an agent — but that is the agent's condition, not Runopsy's.
Runopsy's key
to add a model to the diagnosis		 Yours. runopsy setup puts it in the operating system's credential store, not a file. Almost never. Only for the optional diagnose --mode hybrid.
Runopsy itself works completely without a key. Recording, all 15 checks, ranking, evidence, propagation, the replay experiment, the graph and the web view all run with no key and no network. A key buys exactly one thing: an optional language-model tier that reads the few steps already flagged as suspicious. Without one Runopsy does not fail — it skips that tier and says so.

Where does the data go?

Nowhere. Records, code and output stay in a folder on your machine. Runopsy has no server, requires no account and collects no usage statistics; no part of the product calls a Runopsy-hosted service. The single exception is the --mode hybrid you choose explicitly, and even that sends a summary of a few steps rather than the run, with secrets stripped before anything leaves.

7 · What does it cost?

Three questions any observation tool has to answer: does it spend money, does it slow things down, and what is it for when the assistant already fixes its own mistakes.

Token cost

WhenTokens spent
While recordingZero. Runopsy calls no model; it writes the incoming notice to disk, and that is all.
Diagnosis (default)Zero. All 15 checks, the ranking, propagation and the replay experiment are entirely deterministic.
Diagnosis (--mode hybrid)Only if you ask. You set the ceiling; measured at $0.0003 on a real run.

So by default Runopsy adds nothing to your agent's bill. That is not a preference but an architectural rule: no default check may call a model, and a test enforces it.

Speed cost — and the honest number

Recording starts a separate process for each step the agent takes. That was measured, and it is not free:

MeasurementTime
Recording process per step (this machine)~3.6 s
— of which: loading a recorder cannot avoid~1.6 s
— of which: loading a recorder does not need~0.6 s
In-process recording throughput (bulk)4,858 events/s
Full diagnosis of a 10,000-step run~0.5 s
Almost all of it goes into starting a process, not doing work: recording itself handles thousands of events a second. The measurement also says how much is recoverable — skipping the libraries the hook does not need saves at most 0.6 seconds; the remaining 2.1 s is Python starting and the data schema being built, which a design that opens a process per step cannot avoid. This is therefore not a setting to tune: the real remedy is batching events or keeping a resident recorder. That is today's number and it is printed here; it depends heavily on the machine — bare Python startup here takes 0.45 s, roughly ten times a typical machine.

So what is it for, next to an assistant's auto mode?

Modern assistants already try to fix themselves when they hit an error. When that works you do not need Runopsy. Runopsy exists for the runs where it does not. Concretely:

An assistant's auto modeRunopsy
When it runsDuring the run, on seeing an errorAfter the run, from the record
What it looks atThe error just now — the symptomThe whole run — backwards from the symptom
Who judgesThe same model that made the mistakeDeterministic rules, independent of any model
What it costsEvery attempt burns tokensZero tokens by default
What is left afterwardsA longer logA marked step, its evidence, and a testable claim
If it failsThe budget is spent and you still have the logIt was designed for after the failure

In short: auto mode chases the symptom, Runopsy looks for the onset. In the page 1 example auto mode would have worked on the failing test at step 14 — the fault was at step 9, and nobody stopped there again. The two are not rivals: one acts during the run, the other after it.

It also leaves an audit trail. What auto mode tried disappears when the run ends. Runopsy's record stays on disk, is sealed as it is written, and runopsy verify will tell you whether it was altered afterwards. In a team, being able to answer "what actually happened in that run" is worth something on its own.

8 · Installing, and first use

All you need is Python 3.12 or newer. The paths below get harder in order; you can start with the first and stop there.

Path A — just to see it (no key, no agent, no configuration)

pip install runopsy runopsy demo

The 16-step example from page 1 ships inside the package. demo records it, diagnoses it and prints the result. No network required. Two minutes to see what the tool does.

Path B — your own commands (still no agent)

runopsy record -s "npm ci" -s "npm run build" -s "pytest" runopsy diagnose latest runopsy evidence latest --step 4 # exactly what happened at that step runopsy ui # visual timeline in the browser

record runs the commands you give it, in order, and records each one's exit code and output. If you have a build pipeline or a test chain you need no agent at all.

Path C — with a real coding agent (two commands)

pip install 'runopsy[hermes]' # Runopsy and the agent, one install runopsy init # wires it up, then checks that it took runopsy run "fix the failing test in the payments service"

The quotes matter: square brackets are special in zsh, the default shell on macOS, and without them the command fails with no matches found before ever reaching pip.

init writes the hooks into Hermes' config, installs and enables the plugin that carries token counts, and then checks that it really is wired — the reason that check exists is that a broken setup is invisible. It does not disturb your existing settings: the previous file is copied aside, a config it cannot read is refused rather than edited, and where there is no hooks: section the block is appended as text so your comments and formatting survive exactly.

You put the agent's own model key into Hermes' own config; Runopsy never sees it. If you would rather not have anything written for you, runopsy adapter hermes prints the block and you paste it — that is still the default behaviour.

Path D — adding a language model to the diagnosis (optional, paid)

runopsy setup # key into the OS credential store runopsy diagnose latest --mode hybrid --budget-usd 0.10

Only the few already-suspicious steps go to the model, and the spending ceiling is yours. A local model can be used instead of a key (Ollama / llama.cpp), in which case nothing leaves the machine.

Commands you will actually use

runopsy runslist recorded runs
runopsy diagnose latestdiagnose the last run (--json for machines)
runopsy evidence latest --step Nthe command that ran there and what came back
runopsy graph latestdraw the run as a timeline in the terminal
runopsy replay latest --from-step Nplan the experiment; --execute actually runs it
runopsy verify latestwas this record altered after it was written?
runopsy export latestexport the run in a standard tracing format
runopsy doctoris the installation right, and what is missing

Every command that touches recorded runs accepts --store, and latest always means the most recently started run.

9 · What you see on screen

The output of runopsy demo — the real result for the story on page 1:

Run demo_run — fix the failing test in the payments service demo · 16 events · failed Observed failure (what the run visibly got wrong) step 14 pytest tool 'pytest' failed with exit code 1 Suspected onset (where it may have started going wrong — unvalidated) step 9 write_config tool 'write_config' failed with exit code 1 47% confidence, unvalidated may have reached: step 10, step 11, step 12 and 2 more for evidence: runopsy evidence demo_run --step 9 No cause has been validated yet. To test this candidate, replay from there: runopsy replay demo_run --from-step 9

These states are never conflated

StateWhat it meansHow far to trust it
Observed failureWhat the run visibly got wrong. The test failed at step 14.A fact. Not up for debate.
Suspected onsetWhere it probably broke. Step 9.A guess. Confidence can never exceed 75%.
Replay-supportedThe experiment ran; changing that step made the later failures go away.Now evidenced. Can rise to 90%.
Human-verifiedA person reviewed it and signed off by name.The top level. Never granted without a recorded name.
Why does that distinction matter so much? The easiest thing a diagnostic tool can do is sound certain about something it is not. Send someone confidently to the wrong place once and nobody trusts it again. So Runopsy offers no "definitive root cause": until an experiment or a person says otherwise, it says "suspected". Causal language leaking into an unvalidated finding is treated as seriously as a crash, and there are tests that keep it out.

Evidence: what is behind the claim

runopsy evidence demo_run --step 9

Shows the actual command that ran at that step, the actual output and the exit code — not merely a summary. Content is withheld by default on steps flagged as sensitive; --include-sensitive is required to see it.

The visual view

runopsy ui opens a timeline and failure map in the browser, reachable only from your own machine. Observed order is drawn as a solid line; inferred propagation as a dashed line labelled may reach N% — a guess must not look more convincing than an observation for having been drawn. There is an optional 3D view; it is never the default, and nobody who does not press the button even downloads it.

10 · How it works inside

Five stages, each taking the previous one's output:

1 · RecordEvery step the agent takes sends a notice, which lands on disk.
→
2 · NormalizeDifferent agents' log formats become one common shape.
→
3 · Search15 checks scan the record and mark what looks wrong.
→
4 · RankFindings are scored: severity, how early, how much of what followed they touched.
→
5 · TestThe strongest candidate is re-run in a throwaway copy with one change.
Why does stage 2 exist? Every agent logs in its own format. Runopsy converts them all to one shape, so the analysis never knows which agent it is looking at. The engine contains no agent-specific code — supporting a second agent means writing one more translator and nothing else. The common shape is not invented either: it is compatible with OpenInference, a widely used tracing convention, which is why a run can be exported to other tools.

Stage 3: what do those 15 checks look for?

A sample: did a step return an error code · is the agent running the same command over and over to no effect (it may be stuck) · is it doing something, undoing it and doing it again · did a step time out · does a run that claims success contain a failed step · was a summary handed over when work was delegated · was a configured budget exceeded · does a claim have evidence behind it.

The questions come in five tiers

TierWhat it asksCost
FactsWhat failed, what timed out, what is missing. No interpretation — only what the record says.free
BehaviourPatterns across steps: futile loops, pointless repetition, work that keeps being undone.free
ReachWhat this step may have affected afterwards. Forwards only — nothing can affect the past.free
MeaningA language model reads the few steps already flagged as suspicious. Optional.spends money
ExperimentA re-run in a throwaway copy with one intervention. The only tier that can say "because".free

What does the replay experiment actually do?

It restores the run's state at that moment — that commit, plus the file changes that had not been committed — into a throwaway copy, re-runs from there and changes exactly one thing: it skips the suspected step (--skip-onset) or substitutes a different command (--substitute). The original run is never touched; the experiment is recorded as a new run of its own with a note of what it came from. Anything that could affect the outside world — email, payment, deletion, publishing, remote mutation — is blocked by default, and an unrecognised tool is blocked too, because the gate fails closed.

Why is the record kept in two places?

One is the journal: a plain text file only ever appended to, and the authoritative record. The other is the index: a database for fast queries, entirely rebuildable from the journal. The reason is practical — only one program at a time may write to the database. When an agent splits work across parallel helpers several records arrive at once and the database turns some away, so the journal has to survive that on its own. It is also sealed as it is written, so runopsy verify can say whether the record was altered afterwards.

11 · Who else is in this market? Is the gap real?

There are many tools here, but they answer different questions. By category, with real product names:

Category and examplesThe question it answersWhat it leaves unanswered
Observability
LangSmith · Langfuse · Arize Phoenix · W&B Weave · Braintrust · AgentOps · Helicone · Traceloop		 "What did the agent do?" Every step, every prompt, every token, in searchable dashboards. "Which step started the trouble?" It shows all of them and marks none, so reading the log is still your job.
Evaluation harnesses
Inspect AI · OpenAI Evals · SWE-bench · Ragas		 "How good is the agent?" Pass/fail scores across hundreds of tasks. "Why did it fail?" A score grades the outcome; it does not say where along the way it was lost.
Agent frameworks and assistants
LangGraph · CrewAI · AutoGen · OpenAI Agents SDK · Hermes · coding assistants with auto mode		 "How do I run an agent?" The run itself, its steps, and its attempts to correct itself along the way. What is left when the self-correction does not work. Diagnosis falls to whoever reads the log.
Debuggers
Python pdb · IDE debuggers		 "What is this program doing right now?" Line by line, live. An agent run is not reproducible and it is already over; live stepping does not apply.
Runopsy "Where did it start, what is the evidence, and is that claim true?" Writes no code, holds no conversation, runs no agent. It does not replace yours.

Where the gap actually is

Observability tools record and display. Evaluation harnesses score. Assistants try to correct themselves mid-run. The step in between — reading a finished record, marking one step, and then testing that mark with an experiment — is, as far as we know, not something anyone ships as a product. That is where Runopsy's claim sits.

The evidence that the gap is real comes from the field itself. Academic work asks the same question: TRAIL (Patronus AI) had experts hand-label which step a failure began at in real agent runs, and Who&When did the same for multi-agent runs. That these datasets exist shows "which step is to blame" is considered worth measuring and unsolved. But both are a dataset and a paper, not a tool you install.
In fairness, that research also exposes Runopsy's current weak spot: it is good at finding steps that returned an error, and today it fails on steps that returned nothing wrong and merely decided wrongly. The numbers are on page 9, unhidden.

Why open source, and where would money come from?

Everything that runs locally — the CLI, the engine, recording, replay, the interface, the measurement suite — is Apache-2.0 and works standalone and offline, forever. If a paid tier is ever built it would be a separate server product for teams: shared run history, cross-run trend and regression analysis, access control, audit export, long retention. The rule is explicit — a paid tier may add capability at team scale, but may never remove or cripple anything the local product already does.

13 · Can you trust it? It was measured.

Two terms first. A labelled run is one where the step the failure really began at is known in advance — the answer key is in hand. The hit rate is how often the tool's first guess is right.
MeasurementWhat it testsHit rate
20 constructed runsWhether the ranking works as designed94.4%
— for comparison: blame the last failing stepWhat reading the log bottom-up achieves22.2%
Faults injected into a real recordingWhether it finds a known break in a real run100%
TRAIL — real agent runs, hand-labelled by expertsWhether it agrees with experts on real coding agents0.0%
Who&When — expert-labelled multi-agent runsThe same, on conversational runs0.0%

False alarm rate: exactly zero. A run with nothing wrong produces no finding at all — not approximately zero, exactly, and a test keeps it that way.

Why are those two zeros here? Because they say where the tool does not work, and writing that down is more honest than letting a user discover it.

Runopsy finds steps that themselves errored — in the page 1 example, step 9 had already returned an error code. Across TRAIL's 30 runs, not one of the steps the experts marked errored at all: one wrote its output in the wrong format, one skipped an instruction, one assumed the wrong file path. None of them look like errors; they are just wrong decisions. Runopsy's free tiers read error codes, so they are blind to these by construction. The language-model tier exists for exactly this case — and it has not yet been scored on TRAIL.

What "tested" means here — 931 tests

KindWhat it checks
Real commandsNot mocked: real terminal commands are run and their real exit codes recorded.
Real git repositoriesFile-change tracking is tested against real git, not a stand-in.
32 simultaneous processesProves nothing is lost when recording in parallel. That defect was invisible in a single process.
Wording checksThat no output claims a definite cause for something unvalidated.
A healthy runThat a run with nothing wrong produces no finding at all.
Six real sessionsRuns recorded with a live Hermes agent: two clean successes give zero findings, and the stuck run names its loop as the first candidate.

What is missing today

  • Recording overhead is high. A separate process per step, ~3.6s on this machine. Measured: trimming imports recovers only 0.6s of that, the rest is process startup itself. The remedy is batching or a resident recorder — a design change, not a setting (page 3).
  • 7 of the 15 checks have done work on a real recording. Three never can — they look at information today's agents do not produce.
  • One supported agent (Hermes). The architecture is open to others, but today there is one.
  • Few real runs. Six sessions is not an archive; all were recorded against a single model on small, single-file tasks.
  • The language-model tier is unmeasured. It is the only tier that could answer TRAIL.

In short

When your agent or your pipeline fails a task, Runopsy tells you where to look, shows you why it thinks so, and offers to test whether it is right. It says so when it does not know — and it writes down where it does not work.
