Runopsy

For someone who has never heard of it.

First: what is going on out there?

Some developers now hand their work to AI agents. An agent is a program that carries out a task one move at a time: it reads files, writes code, runs terminal commands, runs tests. We will call each of those moves a step, and the whole thing from beginning to end a run.

Sometimes the agent fails the task. What you are left with is a long log, and the question "where did this go wrong?" to answer on your own.

The problem: where a failure shows is not where it happened

A real example. You tell the agent "fix that failing test." It runs 16 steps:

StepWhat it didResult
1–8Read files, searched, plannedfine
9Wrote a config file for the wrong environmenterrored — and the agent carried on
10–13Edited code, restarted the service, checked itall succeeded
14Ran the testfailed

You read the log bottom-up — everybody does — and you see step 14, the failing test. You spend an hour on that test.

But the fault was at step 9. The agent wrote the wrong address there, the next four steps ran perfectly well, and the thing only blew up at step 14. Nothing in between says "look here", because nothing in between failed.

How often does that mislead you? We measured it on 20 labelled runs. "Blame the last failing step" — reading the log bottom-up — finds the real beginning only 22.2% of the time. Four times in five, you are looking in the wrong place.

What Runopsy does

It quietly records every step while the agent works. When the run ends it reads that record and tells you where things started going wrong — not where they blew up. Then it shows you the evidence, and if you want, it tests its own claim. (The name is Run + Autopsy: an autopsy looks for the cause, not the moment of death.)

Why don't existing tools answer this?

What people use todayWhat it gives youWhat it leaves unanswered
Observability tools
Dashboards that record and display every move an agent makes		 Every step, every detail; searchable, well-drawn Which step started the trouble. It shows all of them and marks none, so reading the log is still your job.
Evaluation harnesses
Systems that test an agent across hundreds of tasks		 Whether the agent passed or failed, in aggregate Why it failed. A score grades the outcome; it doesn't say where along the way it was lost.
Agent frameworks
The runtimes that execute the agent		 The run itself, and its logs Everything after the run. Diagnosis is left entirely to whoever reads the log.
Runopsy A marked onset step, the evidence for it, the steps it reached, and an experiment that tests the claim It writes no code and holds no conversation. It doesn't replace your agent; it attaches to it.

The real difference isn't the visuals — anyone can draw those. It is this: Runopsy tries to refute itself. Having said "it broke at step 9", it re-runs the run in a throwaway copy and changes only step 9. If the later failures really do disappear, a suspicion is promoted to evidence. If they don't, it says so.

What you actually see

Installing is one line, and there is a worked example ready to run — no agent to set up, no API key, no configuration:

pip install runopsy runopsy demo

What comes back is the real output for the story on page 1:

Run demo_run — fix the failing test in the payments service demo · 16 events · failed Observed failure (what the run visibly got wrong) step 14 pytest tool 'pytest' failed with exit code 1 Suspected onset (where it may have started going wrong — unvalidated) step 9 write_config tool 'write_config' failed with exit code 1 47% confidence, unvalidated may have reached: step 10, step 11, step 12 and 2 more for evidence: runopsy evidence demo_run --step 9 No cause has been validated yet. To test this candidate, replay from there: runopsy replay demo_run --from-step 9

Three separate things, and they are never conflated

What it saysWhat it meansHow much to trust it
Observed failureWhat the run visibly got wrong. The test failed at step 14.This is a fact. Not up for debate.
Suspected onsetWhere it probably broke. Step 9.A guess. Confidence can never exceed 75%.
Replay-supportedThe experiment ran: changing that step made the later failures go away.Now evidenced. Can rise to 90%.
Why does that distinction matter so much? The easiest thing a diagnostic tool can do is sound certain about something it isn't. Send someone confidently to the wrong place once and nobody trusts it again. So Runopsy offers no "definitive root cause" — until an experiment or a person says otherwise, it says "suspected".

Using it on your own work

It is useful even with no agent at all. It can wrap whatever you already run:

runopsy record -s "make" -s "pytest" # record your own commands runopsy diagnose latest # where did it start going wrong runopsy evidence latest --step 9 # exactly what happened at that step runopsy ui # visual map in the browser

What happens inside

Five stages. Each takes the previous one's output:

1 · RecordEvery time the agent takes a step, a small notice reaches Runopsy and lands on disk.
→
2 · NormalizeDifferent agents' different log formats become one common shape.
→
3 · Search15 separate checks scan the record: failed steps, futile loops, contradictory states.
→
4 · RankFindings are scored: how serious, how early, how much of what followed they touched.
→
5 · TestThe strongest candidate is re-run in a throwaway copy with one thing changed.
Why does stage 2 exist? Every agent logs in its own format. Runopsy converts them all to one shape, so the analysis never has to know which agent it is looking at. Supporting another agent tomorrow means writing one more translator, nothing else.

Stage 3: what do those 15 checks look for?

A sample: did a step return an error code · is the agent running the same command over and over to no effect (it may be stuck) · is it doing something, undoing it, and doing it again · did a step time out · does a run that claims success contain a failed step · was a configured budget exceeded.

The questions come in five tiers

TierWhat it asksCost
FactsWhat failed, what timed out, what is missing. No interpretation — only what the record says.free
BehaviourPatterns across steps: futile loops, pointless repetition, work that keeps being undone.free
ReachWhat this step may have affected afterwards. Forwards only — nothing can affect the past.free
MeaningA language model reads the few steps already flagged as suspicious. Optional.spends money
ExperimentA re-run in a throwaway copy with one intervention. The only tier that can say "because".free
The first three tiers spend nothing and touch no network — the whole core analysis finishes there. The language model is an optional extra that reads only the few already-suspicious steps; it never ships a whole run to a provider. You set a ceiling on what it may spend.

Why is the record kept in two places?

One is the journal: a plain text file only ever appended to — the authoritative record. The other is the index: a database for fast queries, entirely rebuildable from the journal.

The reason is practical: only one program at a time may write to the database. When an agent splits work across parallel helpers, several records arrive at once and the database turns some away. The journal has to survive that on its own — and it does. It is also sealed as it is written, so runopsy verify can tell you whether the record was altered afterwards.

Why is the project split into eleven pieces?

A user installs all of it with one command (pip install runopsy). The split exists so somebody who wants only the analysis engine inside their own program can take that one piece: core (the engine) · collector (recording) · cli (commands) · replay (the experiment) · bench (measurement) · adapter (attaching to agents) · semantic (the model tier) · server + ui (the web view) · inspect (reading foreign logs).

The rule that matters: the engine contains no agent-specific code. That is what makes supporting a second agent possible at all.

Can you trust it? We measured.

Two terms first. A labelled run is one where the step the failure really began at is known in advance — we hold the answer key. The hit rate is how often the tool's first guess is right.
MeasurementWhat it testsHit rate
20 constructed runsWhether the ranking works as designed94.4%
— for comparison: blame the last failing stepWhat reading the log bottom-up achieves22.2%
Faults injected into a real recordingWhether it finds a known break in a real run100%
TRAIL — real agent runs, hand-labelled by expertsWhether it agrees with experts on real coding agents0.0%
Who&When — expert-labelled multi-agent runsThe same, on conversational runs0.0%
Why are those two zeros here? Because they say where the tool does not work, and writing that down is more honest than letting you discover it.

Runopsy finds steps that themselves errored — in the page 1 example, step 9 had already returned an error code. Across TRAIL's 30 runs, not one of the steps the experts marked errored at all: one wrote its output in the wrong format, one skipped an instruction, one assumed the wrong file path. None of them look like errors; they are just wrong decisions. Runopsy's free tiers read error codes, so they are blind to these by construction. The language-model tier exists for exactly this case.

What "tested" means here — 916 tests

KindWhat it checks
Real commandsNot mocked: real terminal commands are run and their real exit codes recorded.
Real git repositoriesFile-change tracking is tested against real git, not a stand-in.
32 simultaneous processesProves nothing is lost when recording in parallel. That defect was invisible in a single process.
Wording checksThat no output claims a definite cause for something unvalidated. Treated as seriously as a crash.
A healthy runThat a run with nothing wrong produces no finding at all. The false alarm rate is exactly zero.

What is missing today

  • 7 of the 15 checks have done work on a real recording. Three never can — they look at information today's agents don't produce.
  • One supported agent (Hermes). The architecture is open to others, but today there is one.
  • We have no labelled archive of our own. Filling one takes a person reading real failures and saying where each began. Doing it from inside the project would grade the tool against its own opinion.
  • The language-model tier is unmeasured. It is the only tier that could answer TRAIL, and it has not been scored on it yet.

In short

When your agent fails a task, Runopsy tells you where to look, shows you why it thinks so, and offers to test whether it is right. It says so when it doesn't know — and it writes down where it doesn't work.
